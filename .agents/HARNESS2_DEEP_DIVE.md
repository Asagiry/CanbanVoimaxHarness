## 1. Исполнительное резюме (Executive Summary)

Фреймворк **Harness²** от Google Research решает фундаментальную проблему агентных систем в условиях открытого мира (*open-world generalization*): как адаптировать поведение автономного агента к сложным профессиональным задачам, не прибегая к дорогостоящему дообучению весов модели (fine-tuning) и не полагаясь на наличие эталонных ответов (ground-truth rubrics / test suites).

Под **харнессом (Harness)** понимается вся система компонентов вокруг базовой модели: системные промпты, правила (guardrails), долговременная память, интерфейсы инструментов (tool guidance), библиотеки навыков (skills), субагенты, детерминированные скрипты и хуки/плагины в цикле исполнения инструментов.

Архитектура Harness² основана на двух связанных контурах рекурсии при неизменных весах базовой модели:
1. **Task-Level Recursion (Рекурсия уровня задачи)**: Процесс оптимизации харнесса под конкретную решаемую задачу через трехфазный цикл **Propose – Probe – Compose** (Предложение – Пробирование – Композиция). На основе поведенческого контраста между независимыми прогонами (rollouts) редактор харнесса предлагает изменения, тестирует их на той же задаче и синтезирует итоговый харнесс без привлечения внешней разметки.
2. **Harnessing-Level Recursion (Рекурсия уровня мета-харнессинга)**: Межзадачный контур накопления опыта. Успешно принятые харнессы и извлеченные уроки («дистилляция опыта») сохраняются в персистентную библиотеку домена (`Library`), направляя будущие адаптации на схожих задачах.

```text

|                      HARNESS² DUAL-RECURSION ARCHITECTURE                   |
+-----------------------------------------------------------------------------+
|                                                                             |
|  [Harnessing-Level Recursion: Inter-Task Domain Library]                    |

|         | Experience Reflection (Lessons learned)            v Prior Domain |

|  +------v----------------------------------------------------v-----------+  |

|  |                                                                       |  |
|  |                   +-----------------------+                           |  |
|  |                   |    Base Rollout(s)    |                           |  |
|  |                   +-----------+-----------+                           |  |
|  |                               |                                       |  |
|  |                               v                                       |  |
|  |               +-------------------------------+                       |  |
|  |               | Proposer (Evidence Workspace) |                       |  |
|  |               |   * Invariant Edits (INV)     |                       |  |
```

## 2. Анатомия 8 компонентов харнесса (The 8 Harness Components)

Harness² формализует окружение агента как строго типизированное дерево из 8 компонентов (`Tree = dict[str, str]`), разделенных по времени жизни и вычислительной стоимости:

| Номер | Компонент | Путь (OpenCode / Codex) | Время нахождения в контексте | Семантическая роль |
|---|---|---|---|---|
| **C1** | **System Prompt** | `systemprompt.md` / `AGENTS.md` | **Always-On** (в каждом токене) | Базовая роль агента, протокол рассуждений, формат ответов. |
| **C2** | **Guardrails** | `guardrails.md` / `AGENTS.md` | **Always-On** (в каждом токене) | Жесткие постоянные ограничения и правила верификации. |
| **C3** | **Memory** | `LongTermMEMORY.md` / `AGENTS.md` | **Always-On** (в каждом токене) | Долгосрочные универсальные факты о домене. |
| **C4** | **Tool Guidance** | `tool_guidance.md` / `AGENTS.md` | **Always-On** (в каждом токене) | Руководство по эффективному использованию инструментов. |
| **C5** | **Skills** | `skills/<name>/SKILL.md` / `.agents/skills/` | **On-Demand** (по триггеру) | Многошаговые процедуры, загружаемые только при совпадении триггера. |
| **C6** | **Subagents** | `sub_agents/<name>/AGENT.md` | **Isolated Context** (по вызову) | Делегирование задач с большим входом и компактным выходом. |
| **C7** | **Scripts** | `scripts/<name>.py` | **Subprocess** (по вызову bash) | Детерминированные Python-утилиты для механических расчетов. |
| **C8** | **Plugins / Hooks**| `plugin/<name>.ts` / `.codex/hooks.json` | **Inside Tool Loop** (события) | Перехватчики цикла инструментов (`PreToolUse`, `PostToolUse`). |

### Разделение сред исполнения (SurfaceSpec)
Harness² параметризует целевую среду через спецификацию `SurfaceSpec`:
- **OpenCode Surface**:
  - Четыре раздельных файла для постоянного контекста (`systemprompt.md`, `guardrails.md`, `LongTermMEMORY.md`, `tool_guidance.md`).
  - Жесткий лимит: `always_on_max = 24,000` символов.
  - Расширения в цикле: TypeScript-плагины в каталоге `plugin/`.
- **Codex Surface**:
  - Единственный постоянный файл: `AGENTS.md`.
  - Ультра-строгий лимит: `always_on_max = 8,000` символов (из-за молчаливого обрезания Codex на 32 КБ и дороговизны каждого шага).
  - Расширения в цикле: JSON-манифест хуков `.codex/hooks.json` (события `PreToolUse`, `PostToolUse`, `SessionStart`, `Stop`).

## 3. Архитектурная дилемма А: Модификация правил и борьба с "Раздуванием" (Anti-Bloat)

### Пользовательский вопрос:
> *«Как Harness² модифицирует правила и промпты? Тупо раздувают rules так, что агент не может в сторону отойти? Как предотвращают взрыв контекста, конфликты правил и когнитивный паралич? В чем разница между Invariant edits и Domain edits?»*

### 3.1. Миф о наивном раздувании против жестких лимитов Harness²
В Harness² **категорически запрещено** бесконтрольно дописывать правила в постоянный промпт. В исходном коде (`tree.py`, `prompts.py`) заложена математически строгая защита от «когнитивного паралича»:

1. **Hard Character Ceilings (`always_on_max`)**:
   В функции `tree.validate()` встроен жесткий валидатор:
   ```python
   if len(body) > cap:
       errs.append(
           f"always-on content is {len(body)} chars, over the {cap} cap; "
           f"{surface.always_on_cap_reason}"
       )
   ```
   Если редактор харнесса превышает лимит (8 000 символов для Codex, 24 000 для OpenCode), **вся предложенная мутация отбрасывается целиком** (`ValueError`).
2. **Правило компенсации («Cut something to pay for it»)**:
   Системная инструкция редактора прямо гласит:
   > *«ALWAYS-ON PROSE IS THE EXPENSIVE OPTION. Every word of it is in context on every run, competing with the agent's own output budget... If you add always-on text, cut something else to pay for it.»*  
   Если агент хочет добавить постоянное правило, он обязан сократить или удалить существующие неэффективные инструкции.
3. **Иерархия рычагов (The Hierarchy of Levers)**:
   Harness² обязывает редактора выбирать самый дешевый по токенам механизм решения проблемы в строгом приоритете:
   - **1. SKILL (Навык по требованию)** — процедура активируется только при возникновении триггера (формат документа, тип задачи). В базовом промпте занимает ровно 1 строку триггера.
   - **2. SCRIPT (Детерминированный скрипт)** — для механических операций, математики, конверсий и валидаций. Выполняется через bash, занимает 0 токенов в контексте мышления LLM.
   - **3. SUBAGENT (Субагент)** — изолированный контекст для задач, где вход большой, а итоговый ответ компактный.
   - **4. PLUGIN / HOOK (Хук цикла инструментов)** — перехватчик внутри рантайма. Перехватывает ошибки и обрезает шумные выводы, не загрязняя постоянный промпт.
   - **5. ALWAYS-ON TEXT (Постоянный текст)** — **последнее прибежище**. Применяется только для предельно кратких универсальных инвариантов.

### 3.2. Автотриггеры и защита от «мертвых навыков» (Autotrigger Invariant)
В Harness² нельзя просто создать файл навыка `skills/foo/SKILL.md`. Валидатор проверяет, упомянут ли навык в `always_on` тексте. Если нет — навык считается мертвым грузом (`dead weight`).  
Механизм `autotrigger()` автоматически пытается прописать строку триггера:
```python
line = "- When {desc}, read .agents/skills/{name}/SKILL.md and follow it.\n"
```
**Но если эта строка приводит к превышению лимита `always_on_max`, автотриггер блокируется, а валидация отклоняет мутацию!** Это гарантирует, что агент физически не сможет накопить больше навыков, чем помещается в его когнитивную память.

### 3.3. Разделение: Invariant Edits (INV) против Domain Edits (DOM)
Harness² разносит оптимизацию по двум строго ортогональным осям, генерируемым независимыми сессиями редактора:

```text
+-----------------------------------------------------------------------------+
|                       ORTHOGONAL REFINEMENT AXES                            |
+--------------------------------------+--------------------------------------+
|  ИНВАРИАНТНОЕ ИЗМЕРЕНИЕ (INV)        |  ДОМЕННОЕ ИЗМЕРЕНИЕ (DOM)            |
|  "Как агент РАБОТАЕТ" (Procedure)    |  "Что знает ЭКСПЕРТ" (Knowledge)     |
+--------------------------------------+--------------------------------------+
| * Протоколы работы с инструментами   | * Модель предметной области          |
| * Анализ кодов ошибок и тайм-аутов   | * Требования к структуре артефакта   |
| * Защита от зацикливаний и спама     | * Специфика целевой аудитории        |
| * Создание скриптов в scripts/*.py   | * Правила принятия решений           |
| * Хуки в .codex/hooks.json           | * Навыки для типов документов        |
|                                      |                                      |
| [X] ЗАПРЕЩЕНО: добавлять правила     | [X] ЗАПРЕЩЕНО: менять процедуры,     |
| предметной области, факты дела.      | инструменты, скрипты, хуки, лимиты.  |
+--------------------------------------+--------------------------------------+
```

#### Фаза агрегации (Harness Composer / Aggregate)
После генерации $k$ вариантов INV и $k$ вариантов DOM, фаза композиции (`aggregate` в параллельном режиме или `compose_round` в последовательном) объединяет изменения:
- Опирается на контраст траекторий: если ошибка произошла лишь в 1 из $k$ прогонов, это признается случайным шумом, и правило **не вносится** (защита от переобучения на единичный выброс / *overfitting to noise*).
- Вносятся только те правила, которые устраняют систематические сбои, повторившиеся на нескольких прогонах.

## 4. Архитектурная дилемма B: Обработка ошибок инструментов и поведенческий контраст

### Пользовательский вопрос:
> *«Как обрабатываются ошибки инструментов и сбои исполнения? Чинят ли через патчинг промптов, динамическую диагностику возврата инструментов или контрастное пробирование? Как поведенческий контраст сравнивает упавшие и успешные роллауты?»*

### 4.1. Многоуровневая обработка ошибок
Harness² отвергает наивный подход «на каждый чих дописывать правило в промпт». Обработка ошибок распределена по трем уровням:

1. **Динамический перехват в цикле инструментов (Runtime Hooks / Plugins)**:
   Вместо изменения системного промпта создается хук `PostToolUse` в `.codex/hooks.json` или плагин в `plugin/`.
   - Если инструмент возвращает гигантский вывод (>500 строк), хук обрезает его до компактной выжимки (защита контекста от переполнения).
   - Если инструмент падает с известным кодом ошибки (например, синтаксическая ошибка SQL или ошибка компилятора), хук перехватывает ответ и инжектирует точечную подсказку (*targeted hint*) непосредственно в ответ инструмента. Модель видит ошибку и подсказку «по месту», а постоянный системный промпт остается чистым.
2. **Детерминированные скрипты-помощники (`scripts/*.py`)**:
   Если агент в траектории пытается вручную написать сложную команду извлечения данных (например, цепочку regex, jq или awk) и регулярно ошибается, редактор харнесса выносит эту логику в отдельный протестированный Python-скрипт. Агенту дается четкая инструкция вызывать готовый скрипт вместо генерации хрупкого однострочника.
3. **Одноразовый откат (1-Retry Fallback Contract)**:
   При выполнении самого редактора харнесса (`proposer.py`, `recursion.py`) действует строгое правило:
   ```python
   for attempt in range(1, STAGE_ATTEMPTS + 1):
       # Если предложенный харнесс не валиден (синтаксис, превышение лимита, утечка):
       # Дается ровно 1 попытка исправления с инжекцией ошибки в промпт.
   # При повторном сбое -> fell_back = True, наследуется предыдущий стабильный харнесс!
   ```
   Это предотвращает зависание конвейера и порчу рабочей конфигурации.

### 4.2. Поведенческий контраст (Behavioral Contrast) без Ground Truth
Ключевая инновация Harness² — самооценка и анализ траекторий **в условиях полного отсутствия эталонных ответов и тестовых вердиктов**.

В модуле `context.py` реализована строгая изоляция:
```python

    # Если обнаружен маркер грейдера в тексте или имени файла — немедленный отказ!
```

#### Как работает механизм поведенческого контраста:
1. **Файловое пространство улик (`Evidence Workspace`)**:
   Редактор харнесса не получает гигантский контекст в единый промпт. Создается файловая структура на диске (`context/`):
   - `context/task.md` — формулировка задачи.
   - `context/rollouts/<label>.md` — полные траектории прогонов (без урезания).
   - `context/deliverables/<label>/` — сгенерированные артефакты (текстовые конверсии документов, таблицы, изображения, код).
   - `context/pool/<label>/harness.diff` — unified diff между базовым харнессом и харнессом кандидата.
2. **Сравнение расхождений (Divergence Mining)**:
   Промпт композитора инструктирует модель ранжировать находки:
   - **Divergence (Расхождение прогонов)**: если при базовом харнессе Прогон 1 выполнил шаг правильно, а Прогон 2 ошибся — значит, модель *уже обладает способностью* решить задачу, ей просто не хватило четкой фокусировки. Это **самый дешевый и надежный выигрыш**.
   - **Repeated Failure (Систематический сбой)**: если все прогоны упали на одном и том же месте, это дефект текущего харнесса, требующий структурного вмешательства (скрипт или хук).
   - **Isolated Glitch (Одиночный сбой)**: дефект в 1 из $k$ прогонов при $k >= 3$ признается случайной стохастикой и игнорируется, чтобы избежать раздувания правил.
3. **Слепой арбитраж результатов (Blind Deliverable Selection)**:
   Для выбора лучшего итогового арбитражного прогона (`selection.py`):
   - Артефакты анонимизируются случайными метками (`A`, `B`, ...).
   - Независимый оценщик-пропозер (`select`) читает артефакты и выбирает победителя с обоснованием в блоке `<why>`.

## 5. Архитектурная дилемма C: Экономика токенов и модульный контроль затрат

### Пользовательский вопрос:
> *«Кому-то нужен ретро, а кому-то не хочется токены тратить на ретро и улучшение. Как Harness² управляет бюджетом (k rollouts, parallel vs sequential mode, caching, zero-shot fallback)? Как сделать это на 100% модульным в Kanban-пайплайне (быстрая доска vs сложная доска с колонкой ретро)?»*

### 5.1. Формула бюджета Harness²
В модуле `ledger.py` зафиксирована строгая математическая зависимость затрат от параметра масштабирования $k$:

- **Число роллаутов (Rollouts):** $R = 4k$
- **Число сессий редактора (Proposer Sessions):** $P = 3k$

Где:
- $k$ — бюджет рекурсии (число кандидатов / глубина итераций).
- **Rollouts ($R = 4k$)**:
  - $k$ базовых прогонов (reference rollouts).
  - $k$ прогонов кандидатов Invariant (INV).
  - $k$ прогонов кандидатов Domain (DOM).
  - $k$ прогонов итоговых композиций (AGG / Final).
- **Proposer Sessions ($P = 3k$)**:
  - $k$ сессий генерации INV-харнессов.
  - $k$ сессий генерации DOM-харнессов.
  - $k$ сессий агрегации / композиции.

### 5.2. Сравнение режимов: Parallel ("agg") vs Sequential ("seq")

| Характеристика | Parallel Mode (`--mode parallel`, "agg") | Sequential Mode (`--mode sequential`, "seq") |
|---|---|---|
| **Стратегия поиска** | **Широкий поиск (Width)**: $2k$ независимых параллельных гипотез. | **Глубокий поиск (Depth)**: $k$ последовательных шагов рафинирования. |
| **Параллелизм** | Максимальный. Все кандидаты пробируются одновременно через `ThreadPoolExecutor`. | Линейный. Раунд $t$ ждет завершения роллаута раунда $t-1$. |
| **Wall-clock время** | Минимальное (ограничено лишь задержкой одного роллаута и вызова LLM). | Большое ($k \times \text{время шага}$). |
| **Расход токенов** | $4k$ роллаутов + $3k$ сессий редактора. | $4k$ роллаутов + $3k$ сессий редактора. |
| **Рекомендуемое применение** | Исследование альтернативных подходов, мозговой штурм, архитектурный выбор. | Тонкая шлифовка сложного кода, устранение регрессий шаг за шагом. |

### 5.3. Механизмы экономии токенов в Harness²

1. **Оптимизация "Trivial Selection" при $k = 1$**:
   В `selection.py` реализована критическая оптимизация:
   ```python
   if pool_policy == "finals" and k == 1:
       sel = selection.trivial_selection(...)
   ```
   Если $k=1$, на этапе выбора победителя **НЕ вызывается LLM-селектор**! Единственный сгенерированный финальный артефакт принимается автоматически. Это экономит от 5 000 до 30 000 токенов на селекцию.
2. **Контентно-адресуемое кэширование (Content-Addressable Fingerprint Cache)**:
   В `proposer.py` вычисляется SHA-256 хэш от кортежа `(label, mission, system, sha256(context_files))`. Если контекст и входные данные не изменились, результат берется мгновенно с диска с затратами **$0.00** и нулевым расходом токенов.
3. **Файловый буфер вместо промпта (File-Buffered Evidence)**:
   Траектории роллаутов не инжектируются в системный промпт. Они сохраняются на диск, а модель-редактор открывает через инструменты только релевантные фрагменты (`offset`, `limit`, `grep`). Это предотвращает квадратичный рост затрат на контекст.

## 6. Сопоставительный анализ: CanbanVoimaxHarness (.cvh/) vs Harness²

| Архитектурный аспект | Harness² (Google Research) | CanbanVoimaxHarness (.cvh/) | Синергия и выводы для CVH |
|---|---|---|---|
| **Среда и рантайм** | Python 3.12 CLI, запуск через uv, батч-скрипты. | Desktop Rust (Tauri v2) + React 19 UI, легковесный (~40MB RAM), Tokio async. | CVH обладает на порядок более отзывчивым UX и быстрым циклом управления. |
| **Управление задачами** | Линейный запуск бенчмарков (`harness2 --bench jb`), сохранение в папки `runs/`. | **Board-As-Control-Plane**: Канбан-доска — живой контур управления задачами. Колонки = Персоны. | Идеальная среда для визуализации фаз Propose, Probe, Compose и Retro. |
| **Изоляция исполнения** | Временные каталоги `tempfile.mkdtemp()` с копированием контекста. | **Native Git Worktrees**: автономные изолированные деревья `worktrees/<task-slug>`. | Архитектура CVH превосходит Harness², гарантируя чистую изоляцию git и отсутствие конфликтов файлов. |
| **Хранилище диалогов** | Файловая система: `.md` файлы на диске, `summary.json`. | **Высокопроизводительный SQLite (WAL-режим)**: таблица `dialog_items` в `.cvh/harness.db`. | База CVH быстрее и надежнее при конкурентных апдейтах. |
| **Структура правил** | 8 компонентов (C1..C8), жесткий лимит `always_on_max` (8k/24k), автотриггеры. | `.cvh/agents/<role>/persona.md` + файлы в `rules/*.md`. Единый скомпилированный `SystemMessage`. | **Точка роста для CVH**: необходим переход на структуру C1..C8 и внедрение жесткого лимита символов! |
| **Политика инструментов** | Захардкожена в `SurfaceSpec` под OpenCode / Codex. | **Двухуровневая матрица (Two-Level Matrix)**: Global Enabled AND Stage Overrides в `tool-policy.json`. | Матрица инструментов CVH более гибкая и совершенная, чем у Harness². |
| **Ретроспектива и тюнинг** | Рекурсивный модуль `recursion.py` + `library.py` (доменные уроки `INDEX.md`). | Роли `agent-developer-reviewer` и `agent-retro-verifier`, запись в `.agents/task-history/`. | В CVH ретро сейчас описательное, а в Harness² — функционально мутирующее харнесс. |

## 7. Практические рекомендации по внедрению в CanbanVoimaxHarness (.cvh/)

На основе глубинного реверс-инжиниринга Harness² сформулированы четыре конкретные архитектурные модернизации для CanbanVoimaxHarness.

### Рекомендация 1: Модульные Канбан-пайплайны (Быстрая доска vs Доска с Ретро-оптимизацией)
Чтобы удовлетворить требование пользователя («кому-то нужен ретро, а кому-то не хочется токены тратить»):

1. **Preset "Lean Fast Lane" (Нулевые затраты на ретро, $k = 0$)**:
   - Топология: `backlog` -> `dev` (`cvh-dev`) -> `ready`.
   - Задача исполняется в 1 проход базовой моделью. По завершении сразу переходит в `ready`.
   - Дополнительный расход токенов на ретроспективу: **0 токенов**.
2. **Preset "Standard Engineering" (Качественный контроль, $k = 1$)**:
   - Топология: `backlog` -> `dev` -> `review` (`agent-developer-reviewer`) -> `ready`.
   - Reviewer проверяет код через Runtime Sensors (`cargo check`, `pnpm run build`).
   - Если `APPROVED`, задача завершается.
3. **Preset "Autonomous Recursive Tuning" (Полный цикл Harness², $k >= 1$)**:
   - Топология: `backlog` -> `dev` -> `review` -> `retro-tune` (`agent-retro-verifier`) -> `ready`.
   - Колонка `retro-tune` запускается **только на этой доске** или по явному флагу пользователя на карточке задачи (`task.enable_retro: true`).
   - Применяется логика Trivial Selection: при $k=1$ не тратится вызов на селектора, а ретро-верификатор выполняет анализ расхождений и сохраняет урок в SQLite.

### Рекомендация 2: Структурная реформа правил агентов CVH (Внедрение стандарта C1..C8)
Текущие файлы в `.cvh/agents/cvh-dev/rules/` рискуют со временем раздуть системный промпт. Рекомендуется реорганизовать правила по стандарту Harness²:

1. **Разделение на Invariant и Domain**:
   - `.cvh/rules/invariants/` (Strict Guardrails: запрет прямого редактирования без тестов, защита worktree, нормализация CRLF).
   - `.cvh/rules/domains/` (Domain Guidance: специфика Rust/Tauri/React, соглашения об именовании, дизайн-система).
2. **Введение жесткого лимита `always_on_max` в движке Rust**:
   В `src-tauri/src/agent.rs` при компиляции `SystemMessage`:
   ```rust
   pub const MAX_ALWAYS_ON_CHARS: usize = 16_000; // ~4000 токенов

   pub fn compile_system_prompt(persona: &Persona, rules: &[RuleFile]) -> Result<String, AppError> {
       let always_on_text = assemble_always_on(persona, rules);
       if always_on_text.len() > MAX_ALWAYS_ON_CHARS {
           return Err(AppError::ContextCeilingExceeded(format!(
               "Always-on rules size ({} chars) exceeds ceiling ({} chars). Prune rules or convert to on-demand skills!",
               always_on_text.len(), MAX_ALWAYS_ON_CHARS
           )));
       }
       Ok(always_on_text)
   }
   ```
3. **Использование каталога `.agents/skills/` с автотриггерами**:
   Все узкоспециализированные инструкции (например, документация по Voxel, настройки сборщика Windows MSVC, миграции SQLite) выносятся в навыки `.agents/skills/<name>/SKILL.md`. В системном промпте остается только однострочный список триггеров:
   ```markdown
   - Когда задача касается 3D-вокселей, загрузи навык `voxel-art`.
   - Когда задача касается SQLite и миграций, загрузи навык `sqlite-expert`.
   ```

### Рекомендация 3: Динамическая диагностика ошибок вместо раздувания промптов
Вместо того чтобы учить агента в промпте «помни, что Windows PowerShell требует экранирования путей...», перенести исправление ошибок в **runtime-перехватчики (Runtime Tool Diagnostics)** в Rust-бэкенде:
- Ошибка `edit_file` (несовпадение строк) уже великолепно решена в CVH (§ 2.28) через 5-уровневый алгоритм нечеткого поиска и посимвольный LCS-diff. Это эталонный пример подхода Harness²: исправление в коде инструмента, а не раздувание промпта!
- Аналогично расширить `execute_command`: при падении сборки Rust с ошибкой заимствования (borrow checker) инжектировать краткую подсказку прямо в `tool_result`, а не хранить трактат по Rust в системном промпте.

### Рекомендация 4: Персистентная библиотека опыта доменов в SQLite
Вместо разрозненных JSON-файлов в `.agents/task-history/` интегрировать таблицу `domain_experience` в `.cvh/harness.db`:
```sql
CREATE TABLE IF NOT EXISTS domain_experience (
    id TEXT PRIMARY KEY,
    domain TEXT NOT NULL,
    task_id TEXT NOT NULL,
    cue TEXT NOT NULL,             -- Ситуационный триггер (когда применять)
    lesson TEXT NOT NULL,          -- Извлеченный урок (что делать / чего избегать)
    evidence TEXT NOT NULL,        -- Доказательство из траектории (какой шаг упал)
    confidence REAL DEFAULT 1.0,
    created_at INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_domain_exp ON domain_experience(domain, created_at);
```
При запуске задачи в определенном домене (например, `rust-backend` или `react-ui`) движок Rust считывает топ-3 наиболее актуальных урока и инжектирует компактный блок в Relay Handoff.

## 8. Архитектурная матрица решений (Decision Matrix)

| Дилемма пользователя | Решение в Harness² | Рекомендуемое решение для CanbanVoimaxHarness |
|---|---|---|
| **Раздувание правил (Rules Bloat)** | Жесткий лимит `always_on_max` (8k/24k chars) + автоматический отказ валидатора. | Добавить проверку `MAX_ALWAYS_ON_CHARS` в Rust-компилятор промптов (`agent.rs`). |
| **Когнитивный паралич** | Иерархия рычагов: Skill по требованию > Script > Subagent > Hook > Always-on. | Вынести узкие правила из `.cvh/agents/*/rules/` в `.agents/skills/`. В промпте оставить только автотриггеры. |
| **Конфликты правил** | Разделение на INV (процедуры/инструменты) и DOM (предметная область). | Разделить правила CVH на `invariants/` (несдвигаемые законы) и `domains/` (специфика подсистем). |
| **Сбои инструментов** | Хуки `.codex/hooks.json` + детерминированные скрипты в `scripts/*.py`. | Динамическая диагностика ошибок в теле возврата `execute_tool` (по образцу § 2.28). |
| **Поведенческий контраст** | Сравнение траекторий на файловой системе (`context/rollouts/`) без ground truth. | Использовать SQLite `dialog_items` для быстрого диффа успешных и упавших шагов в `agent-developer-reviewer`. |
| **Расход токенов на Ретро** | Масштабирование через $k$. При $k=1$ селектор отключается (`trivial_selection`). | **Пайплайн по выбору**: Быстрая доска ($k=0$, без ретро) vs Инженерная доска ($k=1$ с ретро по желанию). |

## 9. Заключение

Исследование подтверждает: Google Research в проекте **Harness²** создал математически выверенную систему рекурсивного самосовершенствования агентов, главная ценность которой — **не раздувание промптов, а дисциплина ограничений**.

Для CanbanVoimaxHarness заимствование принципов Harness² (иерархия рычагов, жесткие потолки символов, разделение INV/DOM и модульность ретроспективы) позволит создать самую быструю, экономичную и устойчивую к деградации десктопную агентную среду.
