### Задача CVH-043: Единый источник правды сессии агента (Ликвидация «Санта-Барбары» вокруг `isRunning`)

#### 1. Текущая проблема
В коде фронтенда статус выполнения агента определяется через костыль из трёх разрозненных флагов в двух разных Zustand-сторах:
```typescript
const isRunning = task.status === 'running' || hasRunningTool || isAgentActive;
```
- `task.status` хранится в `boardStore`.
- `hasRunningTool` и `isAgentActive` вычисляются в `drawerStore`.
- Бэкенд шлёт разрозненные ивенты (`agent:tool_call`, `agent:telemetry`, `task:updated`).
- **Следствие**: Если окно было свёрнуто, ивент потерялся или процесс аварийно завершился, карточка зависает в бесконечном спине («вечно бежит»), а кнопка Stop перестаёт отвечать.

#### 2. Целевая архитектура
1. **Rust Backend (`src-tauri/src/agent/`)**:
   - Ввести централизованный реестр сессий: `AgentSessionRegistry`.
   - Структура сессии:
     ```rust
     pub struct AgentSession {
         pub session_id: String,
         pub task_id: String,
         pub stage_id: String,
         pub started_at: u64,
         pub status: SessionStatus, // Running, Paused, Aborting, Finished
     }
     ```
   - Любой запуск (`run_agent`, `steer_agent`, `subagent`) регистрируется в реестре.
   - При завершении / прерывании сессия атомарно удаляется / обновляется.
   - Единый системный ивент Tauri IPC: `agent:session_status` (шлёт `{ task_id, session_id, status }`).
   - Команда IPC: `get_active_sessions() -> Vec<AgentSessionSummary>` для мгновенной сверки фронтенда при монтировании или фокусе окна.
2. **React Frontend (`src/stores/agentSessionStore.ts` или интеграция в `drawerStore`/`boardStore`)**:
   - Упразднить вычисление статуса по косвенным признакам (`hasRunningTool`, `activeAgentTaskIds`).
   - Селектор: `const isRunning = useAgentSessionStore(s => s.hasActiveSession(taskId));`.
   - Кнопка Stop отправляет `abort_agent_session(taskId)`, гарантированно убивая зарегистрированную Tokio-задачу.

### Задача CVH-045: Вынос базы данных на личную VPS (Синхронизация Дома и Работы без костылей и JSON)

#### 1. Мотивация: отказ от «JSON-костылей» и изоляция данных
- Плодить текстовые `.json` файлы для синхронизации в git-репозитории — костыльно, раздувает коммиты и небезопасно (история промптов, прогоны тулов и внутренние заметки не должны засорять Git-историю проекта).
- Хранить сам бинарный `harness.db` в Git нельзя из-за неразрешимых бинарных мерж-конфликтов.
- **Идеальное архитектурное решение**: Использовать личную VPS как центральный защищённый хаб данных (Single Source of Truth для задач и диалогов), оставив в локальном Git только чистый исходный код и конфиги досок.

#### 2. Архитектурные варианты для реализации на VPS:

##### Вариант А. `sqld` (LibSQL Server в Docker) — РЕКОМЕНДУЕМЫЙ ⭐
- **Что это**: Открытый форк SQLite от авторов Turso, написанный на Rust. Поддерживает протокол SQLite по HTTP/WebSockets и встроенную двустороннюю репликацию.
- **Как поднять на VPS за 1 минуту**:
  ```bash
  docker run -d --name cvh-sqld -p 8080:8080 \
    -v /opt/cvh-data:/var/lib/sqld \
    -e SQLD_AUTH_TOKEN="твой-секретный-длинный-токен" \
    ghcr.io/tursodatabase/libsql-server:latest
  ```
- **Интеграция в Tauri (`src-tauri`)**:
  - В `Cargo.toml` подключается крейт `libsql = { version = "0.6", features = ["replication"] }`.
  - Режим **Embedded Replica**: приложение читает и пишет в локальный файл кэша на диске (скорость остаётся нативной микросекундной, UI не лагает при плохом интернете), а движок в фоне асинхронно синхронизирует транзакции с `http://vps-ip:8080` по токену.
  - Если на ноутбуке нет интернета — работаешь офлайн. Появился интернет — все изменения автоматически улетели на VPS и подтянулись на втором ПК.

##### Вариант Б. Легковесный Rust-микросервис `cvh-sync` (Axum) на VPS
- На VPS поднимается минималистичный сервис на Axum (Rust), хранящий базу данных на сервере.
- Десктопные клиенты авторизуются по токену и синхронизируют снапшоты/дельты при старте и закрытии приложения.

##### Вариант В. Прямое удалённое подключение (PostgreSQL / LibSQL Remote)
- Перевод стораджа в `src-tauri/src/db.rs` на работу с удалённой базой по защищённому TLS-каналу (WireGuard/Tailscale или HTTPS).

#### 3. Настройки в UI (Десктоп)
- В модальном окне настроек (`SettingsModal.tsx`):
  - Переключатель: `Включить VPS-синхронизацию`
  - Поле: `VPS Endpoint` (например, `https://vps.yourdomain.com:8080`)
  - Поле: `Auth Token` (хранится в заигноренном файле `.cvh/llm.json` или системном хранилище ключей).

### Задача CVH-046: Защита агентов от дум-скроллинга и распил тестовых гигантов

#### 1. Проблема («Doom-Scroll Trap»)
В ходе работы агенты попадают в ловушку бесконечного последовательного чтения (по 30-50 строк через `read_file`), пытаясь найти конец файла или нужный тест, сжигают контекст, ловят деградацию внимания и падают с `Failed edit` на замене скобок в конце файла.
Главные катализаторы:
1. Монолитные тестовые файлы:
   - `src-tauri/src/commands/tests.rs` — **3 896 строк**
   - `src-tauri/src/agent/tests.rs` — **3 985 строк**
2. Отсутствие в `read_file` возможности посмотреть хвост файла (`tail`).
3. Отсутствие атомарного инструмента для добавления кода в конец файла без риска сломать разметку (`append`).

#### 2. План реализации
1. **Декомпозиция тестов на модули (Clean Code для тестов)**:
   - `commands/tests/`: `tasks_tests.rs`, `cortex_tests.rs`, `boards_tests.rs`, `dialogs_tests.rs`, `git_tests.rs`.
   - `agent/tests/`: `engine_tests.rs`, `compactor_tests.rs`, `tools_tests.rs`, `telemetry_tests.rs`.
   - Размер каждого модуля не должен превышать 300–400 строк.
2. **Поддержка отрицательного offset (`tail`) в `read_file`**:
   - В `src-tauri/src/agent/tools/file_ops.rs` поддержать отрицательный `offset`: при `offset: -50` отдаются последние 50 строк файла с честными абсолютными номерами строк.
3. **Атомарный `append_to_file` (или флаг `append: true` в `write_file`)**:
   - Позволяет агенту за 1 вызов гарантированно дописать тест или функцию в конец файла без вызова `edit_file` и риска несовпадения строк.
4. **Anti-Doom-Scroll Guard в ReAct-движке**:
   - Если агент делает $\ge 3$ последовательных вызовов `read_file` одного и того же файла со сдвигом офсета, движок возвращает предупреждение-подсказку с предложением использовать `grep` или отрицательный `offset`.

### Задача CVH-048: Исправление окружения команд на Windows и устранение шума в тестах

#### 1. Проблема запуска команд и кракозябр в `run_scoped_command`
- **Ненайденный `pnpm`**: Когда агент на Windows запускает `pnpm test` через инструмент `bash` (`run_scoped_command`), `cmd.exe` падает с кодом 1, так как `pnpm` часто установлен в пользовательских директориях (`%USERPROFILE%\.cargo\bin`, `%APPDATA%\npm`, `%LOCALAPPDATA%\pnpm`), которых нет в урезанном системном PATH дочернего процесса Tauri.
- **Кракозябры в STDERR (`"pnpm"  ...`)**: `cmd.exe` при сбое внутреннего резолвера команд выводит системное сообщение в кодировке OEM (CP866 на русской Windows), а Rust-бэкенд считывает буфер через `String::from_utf8_lossy`, превращая русский текст в знаки вопросов.
- **Решение**:
  1. В `src-tauri/src/agent.rs` в `run_scoped_command` перед запуском `cmd.exe` гарантированно обогащать переменную окружения `PATH` стандартными путями:
     - `%APPDATA%\npm`
     - `%LOCALAPPDATA%\pnpm`
     - `%USERPROFILE%\.cargo\bin`
     - `C:\Program Files\nodejs`
  2. Добавить resilient fallback декодирования: при ошибке декодирования UTF-8 пробовать декодировать через `encoding_rs::WINDOWS_1251` или `IBM866`, чтобы агенты получали читаемые русские ошибки вместо кракозябр.

#### 2. Варнинги в тестах Vitest (`[boardStore] saveCurrentBoard aborted: boards are not loaded yet!`)
- **Причина**: В `src/stores/__tests__/cortexStore.test.ts` в хуке `beforeEach` состояние `useBoardStore` инициализируется полями `boards`, `columns`, `tasks`, но забыто поле `isBoardsLoaded: true` (оно остаётся `false`).
- При вызове методов персон (`loadAgentPersonas`, `setAgentPersonaColor`, `setAgentPersonaIcon`) стор пытается каскадно обновить цвета доски через `saveCurrentBoard`, который проверяет `if (!isBoardsLoaded)` и пишет `console.warn` в STDERR.
- **Решение**: В `src/stores/__tests__/cortexStore.test.ts` в `beforeEach` явно прописать `isBoardsLoaded: true`.

### Задача CVH-049: Исправление кружка контекста (ContextGauge), протокола ревьюера и Windows-команд

#### 1. Невидимый кружок прогресса контекста в тёмной теме (`ContextGauge.tsx`)
- **Проблема**: На шкале контекста процент пишется (`21%`), но кружок рядом с ним выглядит абсолютно пустым/незаполненным.
- **Причина в коде**: В `src/components/drawer/ContextGauge.tsx:477-481` зашит расчет цвета:
  ```typescript
  const strokeColor = useMemo(() => {
    if (percent < 60) return '#171717'; // <-- ЧЁРНЫЙ ЦВЕТ ДЛЯ СВЕТЛОЙ ТЕМЫ!
    if (percent <= 85) return '#f59e0b';
    return '#ef4444';
  }, [percent]);
  ```
  Цвет `#171717` передается напрямую в `stroke={strokeColor}`. В тёмной теме подложка кружка окрашена в серый (`dark:stroke-[#21262d]`), а сам фон тулбара — почти чёрный (`#07090e` / `#0d1117`). 
  В результате при здоровом контексте (<60%) дуга прогресса рисуется **чёрным цветом** поверх тёмного фона — она темнее самой подложки и для человеческого глаза полностью сливается с пустотой!
- **Решение**:
  - Сделать цвет заполнения видимым и адаптивным: для нормального контекста (<60%) использовать акцентный изумрудный (`#10b981`) или небесно-голубой (`#38bdf8` / `#58a6ff`), либо учитывать класс `dark` (`isDark ? '#38bdf8' : '#0284c7'`).

#### 2. Ложная тревога ревьюера: путаница `main..HEAD` с `main...HEAD`
- **Проблема**: Ревьюер проверяет изменения ветки через `git diff main..HEAD` (две точки). Когда `main` уходит вперёд (добавлены коммиты в хендоф или правила), ревьюер видит минусы в `HANDOFF.md` и паникует: *«Разработчик удалил хендоф и правила!»*, хотя разработчик их не трогал.
- **Решение**:
  - В правилах ревьюера (`.cvh/agents/reviewer/rules/review-checklist.md` и `role-reviewer.md`) закрепить инвариант:
    1. Проверять дифф строго через `git diff main...HEAD` (три точки) — это честный дифф ветки от точки ответвления.
    2. Перед проведением ревью автоматически выполнять `git merge main` в ворктри ветки, чтобы подтянуть свежую базу без ложных срабатываний.

#### 3. Падение линуксовых пайпов (`wc -l`) на Windows
- **Проблема**: Ревьюер или разработчик вызывает `git show ... | wc -l`. В `cmd.exe` утилиты `wc` нет, команда падает с кодом 255 и кракозябрами в консоли.
- **Решение**:
  - В правила персон (`role-developer.md`, `role-reviewer.md`) добавить Windows-инвариант: на Windows запрещено использовать линуксовые утилиты (`wc`, `grep`, `sed`, `awk`). Для подсчета строк или фильтрации использовать флаги самого гита (например, `git log --oneline | find /c /v ""`, либо нативные команды через PowerShell/Node).
