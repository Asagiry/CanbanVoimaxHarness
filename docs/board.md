# 📋 Архитектура Kanban-досок и маршрутизации (docs/board.md)

> **CanbanVoimaxHarness (CVH)** превращает Kanban-доску в интерактивную панель управления (Control Plane).
> Колонки доски — это не пассивные списки статусов, а **автономные агенты** с жестко определенными ролями, политиками и маршрутами.

---

## 1. Архитектура досок и колонок: Колонки = Агенты

В традиционных таск-трекерах (Jira, Trello, Linear) колонка — это просто метка статуса задачи. В CanbanVoimaxHarness действует фундаментальный инвариант:

### **Инвариант: Колонки представляют агентов**
- Каждая колонка может обладать связанной персоной (`persona: "<role>"`).
- Перемещение карточки в колонку инициирует событие `agent:autorun` и вызывает `run_agent(taskId)` через Tauri IPC.
- Агент этапа получает изолированный контекст, настроенный именно под эту колонку:
  - **Персона**: системный промпт и правила из `.cvh/agents/<role>/persona.md` и `.cvh/agents/<role>/rules/*.md`.
  - **SVG-Иконка**: векторная иконка Lucide, заданная в frontmatter или JSON setting.
  - **Модель**: переопределение LLM (`modelOverride`), если для этапа нужна более быстрая или более мощная нейросеть.
  - **Температура**: детерминированная для аудита (0.1) или креативная для концептов (0.4).
  - **Разрешенные инструменты**: срез доступных тулов согласно `tool-policy.json` и `allowedTools`.
  - **Переходные скрипты**: хуки `on_enter` для подготовки окружения.

### Анатомия схемы колонки (`PipelineColumn`)
```json
{
  "id": "review",
  "title": "Ревью кода",
  "color": "#8b5cf6",
  "icon": "CheckSquare",
  "persona": "reviewer",
  "contextWindow": 200000,
  "modelOverride": "gemini-3.8-flash-high",
  "temperature": 0.1,
  "gatekeeperSensor": "cargo check",
  "allowedTools": ["execute_command", "read_file", "glob", "grep", "subagent"],
  "hooks": {
    "on_enter": ".cvh/hooks/on_enter_review.bat"
  },
  "routes": {
    "on_approved": "retro",
    "on_changes_requested": "dev"
  },
  "autoRun": true,
  "terminal": false
}
```

## 2. Фундаментальный инвариант: Backlog → Ready

В CanbanVoimaxHarness жизненный цикл любой инженерной задачи подчиняется строгому закону однонаправленного прогресса и жестким границам доски:

```text
[ Бэклог (backlog) ] ────────► [ В разработке (dev) ] ────────► [ Ревью (review) ]
                                      ▲                               │
                                      │       CHANGES_REQUESTED       │
                                      └───────────────────────────────┤
                                                                      │ APPROVED
                                                                      ▼
[ Готово (ready) ]   ◄───────────────────────────────────── [ Ретро (retro) ]
```

### 2.0 Создание задач и поддержка визуальных вложений (Task Creation & Vision Attachments)
- **Модальное окно создания задачи (`New Task Modal`)**: развернуто до `w-[620px] max-w-[95vw] max-h-[90vh]` с flex-column компоновкой и изолированным внутренним скроллом.
- **Поле описания**: увеличено до `rows={6} min-h-[130px] resize-y` с расслабленной типографикой `leading-relaxed font-sans`.
- **Вставка из буфера обмена (Ctrl+V / Ctrl+М)**: перехват скриншотов из буфера для латинской (`Ctrl+V`) и кириллической (`Ctrl+М`) раскладок, а также fallback через `navigator.clipboard.read()` при фокусе вне текстовых полей.
- **Компрессия изображений**: клиентское масштабирование через `compressImageFile(file, 1568, 0.85)` (максимум 1568px, JPEG 0.85) перед отправкой через Tauri IPC.
- **Интерактивная галерея**: миниатюры вложений с кнопкой удаления `×` и открытием в лайтбоксе (`ImageLightboxModal`).
- **Vision-контекст агентов**: вложения сохраняются в SQLite (`tasks.attachments`), передаются в `AgentSessionConfig.task_attachments` и обогащают нулевой ход LLM через `ChatMessage::user_with_images`.
- **Индикаторы на доске**: карточки на доске отображают лаконичный счетчик `📎 count`, а Task Objective Card в диалоге рендерит интерактивные превью с вызовом лайтбокса.

### 2.1 Неприкосновенность границ (Backlog-to-Ready Invariant)
- **Колонка `backlog` (позиция 0)**: Всегда гарантирована как начальная точка пайплайна. Не может быть удалена или переименована ни пользователем через UI, ни агентами через мутацию конфигурации.
- **Колонка `ready` (последняя позиция, `terminal: true`)**: Всегда гарантирована как финальная точка сдачи. Не может быть удалена или переименована.
- **Автоматическое самовосстановление**: Функция `normalize_pipeline_columns` в ядре Rust инспектирует структуру досок при каждом сохранении и загрузке. Если `backlog` или `ready` отсутствуют, повреждены или смещены, система восстанавливает их на положенные позиции.

### 2.2 Этапы жизненного цикла и Relay Handoff
1. **Входная точка — Бэклог (`backlog`)**:
   - Задачи создаются здесь вручную или через декомпозицию.
   - В бэклоге агенты не вносят изменений в код; разрешены только инструменты поиска и чтения.
2. **Активная разработка (`dev`)**:
   - Для задачи создается изолированный Git worktree (`worktrees/<task-slug>`).
   - Агент-разработчик пишет код, запускает сенсоры и добивается прохождения тестов.
   - Для передачи задачи на аудит используется тул `advance_task(summary)` с обязательным саммари достигнутых результатов.
3. **Независимый аудит (`review`)**:
   - Проводится независимой персоной без доступа к инструментам редактирования файлов.
   - **Relay Handoff**: Саммари разработчика передается аудитору через системный баннер `### [ЭСТАФЕТА ПАЙПЛАЙНА / RELAY HANDOFF]`.
   - При замечаниях вызывается `reject_task(reason)`, возвращающий карточку в разработку с контекстом правок.
   - При успешном прохождении вызывается `advance_task(summary)` или выносится вердикт `APPROVED`.
4. **Ретроспектива и фиксация (`retro`)**:
   - Фиксация задачи в реестре истории (`.agents/tasks-history.json`), обновление графа знаний и правил проекта.
5. **Терминальная точка — Готово (`ready` / `done`)**:
   - Ворктри безопасно удаляется, изменения влиты в целевую ветку, статус задачи переходит в `done`.

## 3. Мульти-доски (`.cvh/boards.json`)

CanbanVoimaxHarness поддерживает несколько независимых досок в рамках одного проекта. Это позволяет вести разработку кода, создание 3D-ассетов и маркетинговые задачи в параллельных специализированных пайплайнах.

### 3.1 Конфигурация мульти-досок (`.cvh/boards.json`)
```json
{
  "activeBoardId": "development",
  "boards": [
    {
      "id": "development",
      "name": "Инженерная разработка",
      "columns": [ ... ]
    },
    {
      "id": "3d-assets",
      "name": "Создание 3D моделей",
      "columns": [ ... ]
    }
  ]
}
```

### 3.2 Встроенные шаблоны досок
При создании новой доски или инициализации проекта доступны готовые архитектурные шаблоны (`get_board_template_columns`):

- **`development` (Инженерный)**:
  - 5 стадий: `backlog` → `dev` → `review` → `retro` → `ready`.
  - Полный цикл с аудитом качества, сенсорами компиляции и ретроспективой.
- **`modeler` / `3d` (3D Ассеты и воксели)**:
  - 4 стадии: `concept` (генерация и референсы) → `modeling` (создание сетки) → `texturing` (материалы и текстуры) → `ready` (экспорт FBX/GLTF).
- **`kanban` / `simple` (Упрощенный)**:
  - 3 стадии: `todo` → `in_progress` → `ready`.
  - Для простых задач и быстрого прототипирования.
- **`empty` (Минимальный)**:
  - 2 стадии: `backlog` → `ready`.
  - Чистый лист для создания собственной схемы с нуля.

### 3.3 Синхронизация с `pipeline.json`
Для обратной совместимости активная доска всегда автоматически зеркалируется в `.cvh/pipeline.json`. При смене доски в интерфейсе бэкенд на Rust атомарно обновляет оба файла.

## 4. Автороутинг между стадиями по вердиктам

Маршрутизация задач в CVH полностью автоматизирована и управляется распознаванием структурированных вердиктов LLM (`src-tauri/src/commands.rs`).

### 4.1 Иерархия подзадач (Subtask Hierarchy)
Когда задача из колонки `dev` переходит на этап проверки (например, `review`):
1. Родительская задача (`CVH-012`) **остается в колонке разработки** и переходит в статус `waiting_subtask`.
2. Система создает изолированную дочернюю подзадачу: `CVH-012.1 (Ревью кода)` в колонке `review`.
3. Это исключает гонки состояний и гарантирует, что разработчик не продолжит писать код, пока идет ревью.

### 4.2 Обработка вердикта `CHANGES_REQUESTED`
Если ревьюер находит несоответствия инвариантам:
1. Агент этапа ревью формирует в ответе маркер `CHANGES_REQUESTED` с перечнем замечаний.
2. Подзадача `CVH-012.1` помечается как `done`.
3. Родительская задача `CVH-012` разблокируется: `waiting_for_subtask_id: null`.
4. Статус родительской задачи возвращается в `idle`, а вердикт устанавливается в `CHANGES_REQUESTED`.
5. На карточке загорается янтарный бейдж «Требуются правки», и агент разработки может перезапуститься для устранения проблем.

### 4.3 Обработка вердикта `APPROVED` и продвижение вперед
Если ревьюер подтверждает качество кода:
1. В выводе фиксируется вердикт `APPROVED` (или `APPROVED_WITH_CAVEATS`).
2. Проверяется конфигурация переходов колонки: `routes.on_approved`.
   - Если маршрут задан (например, `retro`), создается следующая подзадача `CVH-012.2` на этапе ретроспективы.
   - Если маршрут не задан, задача переходит на следующую по порядку колонку в массиве `columns`.
3. Когда задача достигает колонки с флагом `terminal: true` (или `ready`):
   - Все дочерние подзадачи завершены со статусом `done`.
   - Поле `waiting_for_subtask_id` родительской задачи гарантированно сбрасывается в `null`.
   - Родительская карточка перемещается в колонку `ready` со статусом `done`.
   - Бейдж «Ждем подзадачу» исчезает, отображается зеленый бейдж завершения («Готово»).
   - Срабатывает хук завершения `on_finish_done.bat`, который безопасно закрывает ворктри и удаляет временную ветку.

### 4.4 Визуальная подсветка семейств задач (Bidirectional Highlight)
- Связь между родительской задачей и подзадачами отображается через взаимную подсветку при наведении (hover):
  - При наведении курсора на карточку родителя или любой подзадачи подсвечивается всё семейство (родитель, все его дочерние подзадачи и сестринские подзадачи) фиолетовым ореолом (`ring-2 ring-[#8b5cf6]/50`).
  - Родительская карточка в статусе ожидания отображает лаконичный бейдж `● Ждем подзадачу`, а конкретный идентификатор подзадачи доступен во всплывающей подсказке (`title`). Клик по бейджу открывает консоль подзадачи.
  - Бейдж «Ждем подзадачу» отображается строго на активных нетерминальных карточках (`!isDone && status !== 'done'`) только тогда, когда указанная подзадача действительно находится в процессе выполнения. Если задача завершена или подзадача выполнена, бейдж автоматически скрывается.

Благодаря этой архитектуре процесс разработки становится полностью детерминированным, прозрачным и защищенным от человеческих ошибок.

## 5. Железный инвариант сохранения доски (Ironclad Board Preservation Invariant)

- **Строгая изоляция задач по доскам**: Задачи ОБЯЗАНЫ строго сохранять свой `board_id` при вызовах `advance_task`, завершении циклов агентов (`run_agent`) и перемещении в UI. Самовольный переход («board hopping») между досками категорически запрещен.
- **Локальный контекст пайплайна**: Продвижение задачи через `advance_task` и терминальная финализация осуществляются исключительно по колонкам родной доски задачи (`task.board_id`). Ни при каких обстоятельствах задача не может переноситься на чужую доску только из-за того, что оператор переключил активную вкладку интерфейса или изменился `activeBoardId`.
- **Перемещение через UI**: При перетаскивании карточек на доске стор гарантирует приоритетное сохранение `task.boardId`, исключая подмену идентификатора доски значением глобального фокуса `activeBoardId`.
