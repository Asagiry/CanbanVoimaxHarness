# ponytail: Инженерия минимальных изменений и борьба с оверинжинирингом

Скилл регламентирует принципы предельной простоты кода (KISS/YAGNI) и защиты кодовой базы от избыточных архитектурных нагромождений, необоснованных зависимостей и раздутых диффов.

---

## 1. Фундаментальный принцип

> **"Будь амбициозен в замысле, минималистичен в решениях."**

Сложные задачи решаются простыми и прозрачными механизмами. Создание нового класса, интерфейса или файла допустимо только тогда, когда исчерпаны возможности точечной модификации существующих структур.

---

## 2. Ключевые инженерные инварианты

### 2.1 Инвариант 1–3 строк
- Если дефект или задача закрывается точечной правкой 1–3 строк в существующем файле — изменение вносится строго по месту.
- Запрещено создавать новые файлы сервисов, утилитных функций, контекстов или фабрик ради изолированной микрологики.

### 2.2 Мораторий на сторонние зависимости
- Запрещено добавлять новые crates в `Cargo.toml` или npm-пакеты в `package.json` без явного архитектурного обоснования и согласования.
- Все типовые задачи решаются средствами стандартной библиотеки Rust, Tokio, Tauri v2, существующими зависимостями (`rusqlite`, `serde`, `anyhow`), базовым React 19 и Zustand.

### 2.3 Нулевой спекулятивный "future-proofing"
- Код пишется строго под зафиксированные требования задачи.
- Запрещено закладывать обобщенные параметры "на вырост", фиктивные флаги конфигурации, неиспользуемые перечисления и пустые методы расширения.
- Архитектурная гибкость обеспечивается модульностью и отсутствием жестких связей, а не слоями абстрактных прокладок.

### 2.4 Неприкосновенность безопасности и обработки ошибок
- Ponytail запрещает лишние архитектурные слои, но категорически защищает надежность системного уровня.
- В Rust: строгая типизация ошибок `Result<T, AppError>`, запрет голых `.unwrap()` в продакшн-путях, корректная диспетчеризация задач Tokio и транзакции SQLite остаются обязательными.
- В React: мемоизация селекторов через `useShallow`, корректный жизненный цикл эффектов и обработка пустых списков обязательны.

## 3. Режимы исполнения

### 3.1 Предкоммитный аудит (`/ponytail-review`)
Выполняется перед формированием коммита и вызовом ревьюера:
1. Запуск `git diff` и проверка каждой измененной строки.
2. Проверка: можно ли решить задачу вдвое меньшим объемом кода?
3. Проверка: нет ли добавленных файлов, без которых логика работает так же надежно?
4. Проверка: не затронуты ли файлы и конфигурации, не относящиеся к задаче?

### 3.2 Ревизия подсистемы (`/ponytail-audit`)
Применяется при анализе существующего модуля:
1. Поиск мертвого кода, забытых отладочных веток и дублирующихся алгоритмов.
2. Определение избыточных слоев преобразования данных (DTO -> Model -> ViewState).
3. Формирование рекомендаций по схлопыванию структуры без изменения внешнего API.

---

## 4. Чеклист приемки кода

| Критерий | Допустимо | Нарушение инварианта |
|----------|-----------|----------------------|
| **Новые файлы** | 0–1 файл (при строгой необходимости) | Создан каталог из 4–5 микрофайлов |
| **Зависимости** | 0 новых зависимостей | Добавлен новый crate или npm-модуль |
| **Размер диффа** | Компактный, сфокусированный | Затронуты несвязанные файлы или форматирование |
| **Абстракции** | Прямой вызов функции | Обертка над вызовом ради одного флага |
