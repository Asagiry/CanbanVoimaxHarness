## ⏪ 1. Машина времени: Откат до любого сообщения (Time Travel / Message Rewind)

### Проблема:
В классических AI-ассистентах, если пользователь отправил неудачный steer-промпт («Слушай, перепиши всё на Vue...»), модель начинает генерировать шаги в ложном направлении. Пользователю приходится либо писать: *«Забудь что я сказал, верни назад»* (что засоряет контекст и путает модель галлюцинациями), либо полностью убивать задачу и начинать сначала.

### Концепция решения:
Возможность нажать **«Откатиться сюда» (Rewind to this message)** на любом сообщении в ленте задачи.

#### Уровень 1: Soft Rollback (Диалоговый откат / Стирание памяти)
* **Механика**:
  - Нажатие кнопки «Откат» на сообщении пользователя или шаге агента.
  - Rust-бэкенд выполняет субмиллисекундную транзакцию в SQLite WAL:
    ```sql
    DELETE FROM dialog_items 
    WHERE task_id = ? AND created_at >= (SELECT created_at FROM dialog_items WHERE id = ?);
    ```
  - Сбрасывается оперативная память `AppState::agent_contexts[task_id]`.
  - Следующий запуск агента пересобирает контекст из оставшихся сообщений. Для модели ошибочной ветки **будто никогда не существовало**.
* **Сложность реализации**: 🟢 Низкая (2–3 часа).

#### Уровень 2: Hard Rollback (Полный откат: диалог + код в ворктри)
* **Механика**:
  - Перед исполнением любого пользовательского steer-промпта бэкенд делает скрытый быстрый чекпоинт в изолированном ворктри ветки задачи:
    ```bash
    git add -A && git commit -m "cvh: checkpoint before steer-<id>"
    ```
    Хэш коммита привязывается к записи steer-сообщения в SQLite.
  - При откате:
    1. В папке ворктри задачи (`worktrees/<task-slug>`) выполняется `git reset --hard <checkpoint_hash>`.
    2. База диалогов откатывается по схеме Soft Rollback.
  - **Результат**: и мысли модели, и файлы в рабочей директории возвращаются в точное байт-в-байт состояние на момент до отправки сообщения. При этом основной репозиторий (`main`) находится в 100% безопасности.
* **Сложность реализации**: 🟡 Умеренная (1 рабочий день).

## ⚡ 2. Слэш-команды в строке управления (Drawer Steer Bar)

### Концепция:
Быстрый ввод через символ `/` в поле отправки сообщений с автокомплитом:
- `/review` — отправить задачу на независимый аудит со стандартным чек-листом.
- `/plan` — потребовать от агента опубликовать план через `todo_write` без правок кода.
- `/audit` — запустить поиск уязвимостей и секретов.
- `/compact` — принудительно выполнить сжатие контекста без потери ключевых фактов.
- `/rule <name>` — принудительно загрузить правило в память агента.

## 👁️ 5. fs-observation-policy: Обязательное чтение перед редактированием (Read-Before-Edit)

### Проблема:
LLM часто «вслепую» пытается угадать содержимое файла и вызывает `edit_file` без предварительного чтения. В результате:
- Ошибки `NOT_FOUND` из-за несовпадения отступов, окончаний строк или названий функций.
- Бесполезный расход десятков тысяч токенов на повторные попытки.
- Риск случайного повреждения или порчи кода.

### Концепция решения (по образцу DeepSeek Harness & Claude Code):
1. В `ToolContext` в Rust ведется множество путей файлов, прочитанных или созданных за сессию: `observed_files: Arc<Mutex<HashSet<PathBuf>>>`.
2. Вызовы `read_file`, `fetch_file` или создание нового файла через `write_file` заносят канонический путь в `observed_files`.
3. При вызове `edit_file` (или перезаписи существующего файла через `write_file`):
   - Если файл присутствует в `observed_files` — операция выполняется.
   - Если файл **отсутствует** в `observed_files` — возвращается мгновенная строгая ошибка без модификации диска:
     ```text
     Error: File 'src/agent.rs' has not been inspected yet.
     Under the fs-observation-policy, you must read the file with 'read_file' before modifying it.
     ```
4. Модель сразу дисциплинированно читает файл, получает 100% точный байтовый контекст и выполняет точечный, безошибочный патч с 1-й попытки (100% First-Time-Right).

## 🎛️ 6. Гибкая матрица контекста субагентов (Subagent Context Capacity Matrix)

### Проблема:
Субагенты выполняют принципиально разные задачи: от быстрой проверки синтаксиса на 20 строк до глубокого архитектурного анализа на 80 шагов. Если задавать глобальный жесткий размер контекста в матрице тулов, все субагенты получат одинаковый размер (либо перерасход памяти, либо нехватка контекста).

### Концепция 4-уровневого каскада разрешения контекста:
1. **Уровень 1 (Ролевой setting)**: Субагент читает `.cvh/agents/<role>/setting`. У роли `architect` может стоять 256,000 токенов, у `developer` — 200,000, у `reviewer` — 128,000, у `scout` — 64,000.
2. **Уровень 2 (Параметр вызова инструмента)**: В схему `subagent` / `subagent_bg` добавляется опциональный параметр `context_window?: number`. Если родитель знает, что поручает гигантскую задачу, он явно передает `context_window: 250000`.
3. **Уровень 3 (Глобальная матрица tool-policy.json)**: В настройках `toolSettings.subagent` вводится `default_context_window` (по умолчанию 128,000) для нетипизированных или общих субагентов (`role: "general"`).
4. **Уровень 4 (Наследование от родителя)**: По умолчанию контекстный лимит наследуется от родительской задачи.
