# 🛠️ Авторитетное руководство по инструментам (docs/tools.md)

> **CanbanVoimaxHarness (CVH)** — сверхбыстрая (~40MB RAM) настольная агентная среда и оркестратор на Rust (Tauri v2) и React 19.
> Инструменты (Tools) — это фундаментальные строительные блоки взаимодействия агентов с файловой системой, терминалом, доской Kanban и внешним миром.

---

## 1. Архитектурная модель инструментов в CVH

Исполнение инструментов в CanbanVoimaxHarness подчиняется строгим принципам безопасности, надежности и контекстной гигиены:

1. **Нативное исполнение в Rust (`src-tauri/src/agent.rs`)**:
   - Все стандартные инструменты выполняются асинхронно в Tokio runtime.
   - Пакетное и потоковое управление процессами через `tokio::process::Command` с таймаутами и аварийным сбросом дерева процессов (`taskkill /F /T /PID` на Windows).
2. **Изоляция в Git Worktrees (`worktrees/<task-slug>`)**:
   - Любые файловые и терминальные инструменты исполняются строго внутри изолированной рабочей директории задачи (`CVH_WORKTREE_PATH`).
   - Исходное дерево репозитория защищено от случайных коллизий и неконсистентных состояний.
3. **Двухуровневая матрица политик (Tool Policy Matrix, § 2.5)**:
   - Доступность инструментов рассчитывается по формуле строгой AND-логики между глобальным реестром и правами этапа пайплайна.
   - Запрещенные инструменты вырезаются из JSON-схемы запроса к LLM (**Zero-Trust Request Stripping**), устраняя галлюцинации и экономя до 2 500+ токенов на шаг инференса.
4. **Контекстный спиллинг больших выводов (Output Spilling, § 2.8 & § 2.33)**:
   - Выводы консольных команд, превышающие 500 строк или 64 КБ (и чтения файлов >2 000 строк или 128 КБ), автоматически сбрасываются в `.cvh/spill/<timestamp>-<tool>.log`.
   - В контекст модели возвращается усеченная сводка (20 строк HEAD + 20 строк TAIL) и путь к полному логу.
   - **Исключение (§ 2.33)**: Отчеты субагентов (`subagent`, `subagent_bg`, `collect_subagent`) **никогда не спиллятся**, гарантируя родителю 100% данных для синтеза.

## 2. Полный каталог стандартных инструментов

### 2.1 Навигация по пайплайну и доске (Pipeline Navigation)

| Инструмент | Параметры | Описание |
| :--- | :--- | :--- |
| `advance_task` / `move_task` | `summary?: string`, `stage_id?: string` | Переводит задачу на следующий этап пайплайна или указанный `stage_id`. ВАЖНО: все пункты TODO должны быть полностью завершены перед вызовом. Текст `summary` передается в эстафету Relay Handoff. При успехе завершает ReAct-цикл текущего агента. |
| `reject_task` | `reason: string`, `target_stage?: string` | Возвращает задачу на доработку в предыдущий этап (например, из `review` в `dev`), разблокируя родительскую карточку. |

> 🚨 **Критический ролевой инвариант (§ 2.8, § 2.16)**:
> Создание и удаление карточек задач (`create_task`, `create_tasks`, `complete_task`) строго зарезервированы за **Root Orchestrator (Level 0)** и человеком через интерфейс.
> Субагентам разработки (`cvh-dev`, `developer`, `reviewer`) **СТРОГО ЗАПРЕЩЕНО** вызывать `create_task`, `create_tasks` или `complete_task`. Агенты работают только в пределах назначенных задач и продвигают их через `advance_task` или `reject_task`.

### 2.2 Иерархия делегирования субагентов (Subagent Hierarchy)

| Инструмент | Параметры | Описание |
| :--- | :--- | :--- |
| `subagent` | `role: string`, `prompt: string` | **Синхронный ваншот**: порождает дочернего агента в изолированном Tokio-таске в процессе бэкенда, ожидает завершения и возвращает полный отчет. |
| `subagent_bg` | `role: string`, `prompt: string` | **Асинхронный фон**: мгновенно запускает фонового субагента и возвращает `subagent_id`. |
| `collect_subagent` | `subagent_ids: string[]`, `timeout_seconds?: number` | Ожидает завершения одного или нескольких фоновых субагентов по 3-уровневому каскаду (активные каналы, сессии памяти, SQLite). |
| `subagent_list` | _нет_ | Возвращает реестр активных и завершенных субагентов текущей задачи. |

- **Автономный синтез отчетов (§ 2.32)**: Если субагент завершил вызовы тулов без текстового ответа, движок автономно запускает финальный ход синтеза с `tools: None`, гарантируя содержательный отчет.
- **Изолированный точечный аборт (§ 2.34, § 2.35)**: Остановка субагента оператором через UI или `abort_agent` уничтожает только поток конкретного субагента, не затрагивая родительский ReAct-цикл и соседей.

### 2.4 Файловые операции и консоль ворктри (File & Shell Operations)

| Инструмент | Параметры | Описание |
| :--- | :--- | :--- |
| `read_file` | `file_path: string`, `offset?: number`, `limit?: number` | Построчное чтение UTF-8 файла с номерами строк. |
| `write_file` | `file_path: string`, `content: string` | Полная атомарная запись UTF-8 файла. |
| `edit_file` (`str_replace`) | `file_path: string`, `old_string: string`, `new_string: string`, `replace_all?: boolean` | Точечная замена блоков текста по 5-уровневой иерархии нормализации (§ 2.28). |
| `glob` | `pattern: string`, `path?: string` | Поиск файлов по маске внутри активного ворктри. |
| `grep` | `pattern: string`, `path?: string` | Регулярный поиск содержимого файлов внутри ворктри. |
| `execute_command` (`bash`) | `command: string`, `timeout_seconds?: number` | Запуск консольных команд с контролем времени и перехватом stdout/stderr. |

#### Пятиуровневая иерархия `edit_file` (§ 2.28)
При модификации исходного кода инструмент `edit_file` производит сопоставление в строгом порядке:
1. Точное байтовое совпадение (`current.contains(old_string)`).
2. Адаптация CRLF (в файле `\r\n`, модель прислала `\n`).
3. Обратная адаптация CRLF (в файле `\n`, модель прислала `\r\n`).
4. Нормализация окончаний строк с сохранением исходного формата файла при записи.
5. Whitespace-relaxed сравнение: обрезка краевых пробелов на каждой строке и пропорциональная адаптация отступов.

## 3. Матрица политик: Tool Policy Matrix (§ 2.5)

Контроль доступа к инструментам определяется файлом `.cvh/settings/tool-policy.json`:

```json
{
  "globalEnabled": {
    "read_file": true,
    "edit_file": true,
    "write_file": true,
    "execute_command": true,
    "create_task": false,
    "complete_task": false
  },
  "stageOverrides": {
    "dev": {
      "edit_file": true,
      "write_file": true,
      "execute_command": true
    },
    "review": {
      "edit_file": false,
      "write_file": false,
      "execute_command": true
    }
  }
}
```

- **Формула вычисления прав**:
  `effective(tool, stage) = globalEnabled[tool] && stageOverrides[stage][tool]`
- Если инструмент отключен в `globalEnabled`, **ни один этап не может включить его локально**.
- При сохранении политик через UI бэкенд синхронизирует разрешенные инструменты в YAML-шапку `.cvh/agents/<role>/persona.md` (`tools: [...]`).

## 4. Пользовательские инструменты (Custom Tools, `.cvh/tools/`)

Пользовательские инструменты позволяют подключать любые внешние скрипты или CLI-утилиты без изменения исходного кода бэкенда.

### 4.1 Формат дескриптора инструмента
Каждый кастомный инструмент описывается отдельным файлом `.cvh/tools/<tool_name>.json`:

```json
{
  "name": "cargo_clippy",
  "description": "Запуск анализатора кода Clippy с автоисправлением в ворктри",
  "parameters": {
    "type": "object",
    "properties": {
      "fix": {
        "type": "boolean",
        "description": "Применить автоисправление замечаний"
      }
    }
  },
  "command": "cargo clippy --manifest-path src-tauri/Cargo.toml {{args}}"
}
```

- Плейсхолдер `{{args}}` интерполируется переданными аргументами в формате CLI-флагов или JSON.
- Исполнение происходит внутри ворктри с перехватом кодов возврата и защитой от зависания.

## 5. Протокол очистки ворктри (Worktree Teardown Protocol, § 2.23)

При завершении задачи или слиянии в `main` хуки жизненного цикла (`.cvh/hooks/on_review_finish.bat`, `.cvh/hooks/on_enter_ready.bat`, `.cvh/hooks/on_enter_ready.sh`) обязаны выполнять двухшаговый протокол:

```bash
# 1. Дерегистрация и удаление физической папки
git worktree remove "<path>" --force

# 2. Очистка устаревших указателей административной директории
git worktree prune

# 3. Удаление объединенной тематической ветки
git branch -D "<branch>"
```

Этот протокол гарантирует отсутствие предупреждений `prunable` в `git worktree list` и абсолютную чистоту метаданных репозитория.
